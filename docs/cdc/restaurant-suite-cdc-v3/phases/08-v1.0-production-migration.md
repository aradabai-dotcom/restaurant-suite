# CDC-08 — V1.0 : validation, migration et livraison production

**Objectif de sortie :** livrer un package reproductible, maintenable, testable et réversible sur plusieurs sites WooCommerce.  
**Dépendances :** V0.0 à V0.7 validées et rapports conservés.  
**Critère principal :** aucun défaut bloquant connu et rollback démontré.

## 1. Matrice de compatibilité

La validation doit tester les combinaisons supportées de PHP, WordPress, WooCommerce, thème et Elementor définies dans `docs/compatibility-matrix.md`. HPOS est activé dans au moins un environnement. Les blocs Panier/Checkout ne sont annoncés que si les tests spécifiques sont verts ; sinon la documentation les marque comme non supportés ou reportés.

Les tests couvrent produits simples, variables, hors stock, variations à prix différents, taxes, frais, minimum, invité, connecté, mobile, erreurs réseau, JavaScript désactivé, Elementor actif/désactivé, thème sans Elementor, cache, fragments, traductions, extensions de paiement et HPOS.

## 2. Sécurité

Les contrôles couvrent capacités, nonces, validation, assainissement, échappement, upload, accès aux commandes, périmètre restaurant, logs et secrets. Chaque endpoint doit avoir un test de refus. Composer Audit, npm audit, Gitleaks et, si retenu, Semgrep sont exécutés avant release. Les dépendances inutilisées et assets promotionnels hérités sont supprimés.

Un audit manuel vérifie que le prix n’est jamais accepté depuis le navigateur, qu’une commande WhatsApp ne peut pas être dupliquée, qu’un rôle cuisine ou livreur ne peut pas accéder aux réglages généraux et qu’un utilisateur ne peut pas lire les données d’un autre restaurant.

## 3. Performance et accessibilité

Lighthouse CI mesure accueil, menu, fiche produit, panier et confirmation, avec budgets documentés. Les assets conditionnels, dimensions d’image, cache, CSS, JavaScript et Core Web Vitals sont vérifiés. Les objectifs de référence sont LCP ≤ 2,5 s, INP < 200 ms et CLS < 0,1, à mesurer sur des pages réalistes.

axe-core est exécuté sur menu, Quick View, drawer, formulaire WhatsApp et dashboard. Une revue manuelle clavier et lecteur d’écran vérifie focus, Échap, labels, landmarks, ordre de tabulation, contraste et réduction des animations.

## 4. Migration staging

La migration est effectuée sur une copie de staging sauvegardée. Chaque extension concurrente est retirée une seule à la fois, suivie d’un test de régression et d’une comparaison visuelle. Reno est retiré après V0.2, Side Cart après V0.3, OneClick après V0.4, l’ancien dashboard après V0.5, les addons après audit des templates et WPCode après migration et test de chaque snippet utile.

WooCommerce n’est jamais retiré. LiteSpeed Cache reste indépendant si l’hébergement le justifie. Hostinger Tools reste hors du produit restaurant et n’est conservé que si une fonction d’hébergement l’exige.

La production ne sera basculée qu’après validation du staging, fenêtre d’intervention annoncée, sauvegarde vérifiée, plan de retour documenté et responsable disponible pour surveiller les premières commandes.

## 5. Packaging

Le pipeline produit un ZIP du plugin, un ZIP du thème, les fichiers de licence, le changelog, la matrice de compatibilité, le guide d’installation, le guide de rollback et un checksum SHA-256. Le package est installé sur un WordPress vierge et mis à jour depuis une version précédente. Aucun fichier de développement, secret, test sensible ou dépendance inutile ne doit être inclus.

Le numéro de version doit être cohérent dans les headers WordPress, constantes, Composer, package Node et changelog. Les migrations de réglages sont exécutées sur une copie et vérifient qu’elles ne touchent ni catalogue ni commandes.

## 6. Definition of Done V1.0

La V1.0 est prête lorsque le package s’installe sur un nouveau site WooCommerce, affiche le menu, gère Quick View, maintient un panier cohérent, crée une commande WhatsApp unique, permet la gestion selon les rôles, fonctionne avec ou sans Elementor, passe la matrice de tests, respecte les budgets de qualité et peut être restauré sans perte de données.

Tous les jobs CI sont verts, les artefacts sont archivés, les anomalies critiques et majeures sont fermées ou explicitement acceptées, la documentation opérateur est livrée et une personne non impliquée dans le développement peut exécuter l’installation et le rollback.

## 7. Gate de livraison

La livraison production exige une approbation technique, une approbation fonctionnelle du restaurant pilote et une vérification de sauvegarde. Une seule anomalie critique de sécurité, intégrité de commande, accès croisé, perte de données ou impossibilité de rollback bloque la release.

## 8. Rollback production

Le rollback suit cet ordre : désactivation de la fonctionnalité nouvellement livrée si possible, retour au package précédent, restauration des réglages versionnés, vérification des commandes et test du parcours principal. Les commandes créées pendant la fenêtre ne sont pas supprimées automatiquement. Toute intervention est journalisée et communiquée au responsable du site.

## Addendum v2 — politique d’outillage anticipée

La règle officielle est désormais de distinguer **installation**, **première exécution** et **contrôle bloquant**. Lorsqu’un outil peut être installé sans créer de dépendance de production, il est installé dès la phase 0.0. Il n’est exécuté que lorsque la fonctionnalité correspondante existe, et il ne bloque une validation qu’à partir du niveau indiqué dans la matrice.

| Outil | Installation | Première exécution | Bloquant à partir de | Périmètre |
|---|---|---|---|---|
| Infection | 0.0 | Services PHP purs en V0.1/V0.2 | V0.2/V0.3 sur services critiques | Code propriétaire uniquement |
| Rector | 0.0 | `dry-run` dès 0.0 | Avant release/migration PHP | Aucun changement automatique sans revue |
| Psalm | Optionnel 0.0 | Analyse exploratoire du Core | Jamais au démarrage | PHPStan reste principal |
| OWASP ZAP | 0.0 si cible autorisée | Baseline/passif V0.1 | Routes AJAX/REST en V0.4 | Staging autorisé seulement |
| k6 | 0.0 si cible autorisée | Smoke léger V0.1 | Panier/commande en V0.3/V0.4 | Seuils et arrêt d’urgence obligatoires |
| BrowserStack | Optionnel V0.1 | Après premiers composants UI | V1.0 seulement si annoncé | Service distant, pas dépendance locale |
| WP-CLI Doctor | 0.0 | 0.0, 0.7 et 1.0 | Gates de staging/release | Checks personnalisés versionnés |
| Query Monitor | Staging 0.1 | Dès menu disponible | Analyse performance avant release | Jamais dans le ZIP client |
| User Switching | Staging 0.5 | Dès matrice de rôles | Revue manuelle des rôles | Les E2E ne doivent pas en dépendre |
| WP Crontrol | Staging 0.4 | Dès cron/Actions Scheduler | Avant release si cron utilisé | Jamais en production client par défaut |
| WPScan | 0.0/CI | Avant release | Avant chaque release | Cible autorisée uniquement |

L’installation anticipée ne dispense pas des garde-fous : ZAP, k6 et WPScan ne ciblent que le staging autorisé ; les rapports nettoient les secrets ; BrowserStack reste optionnel ; Infection ne mute jamais WordPress ou WooCommerce en entier.

## Addendum v3 — dépôt exécutable avant contrats métier

Le projet distingue désormais deux gates successifs :

1. **Gate de matérialisation du dépôt** : l’arborescence, DDEV, les scripts, les fixtures, le Makefile, les lockfiles et la CI existent et produisent les preuves annoncées.
2. **Gate des contrats métier 0.0** : le contrat de données, les statuts, les permissions, l’idempotence, les événements, les hooks et la matrice de tests sont approuvés.

Le dépôt doit être opérationnel pour accueillir la phase 0.0, mais cette matérialisation ne remplace pas les contrats métier. Aucun code fonctionnel V0.1 ne commence avant l’approbation écrite des contrats 0.0.

### Gouvernance Composer

| Fichier | Responsabilité | Commande de référence |
|---|---|---|
| `composer.json` racine | Outillage global du dépôt, scripts qualité et dépendances communes | `composer install` depuis la racine |
| `composer.lock` racine | Lockfile de l’outillage et de la CI | `composer install --no-interaction --prefer-dist` |
| `plugin/restaurant-suite-core/composer.json` | Autoload et dépendances propres au plugin si nécessaires | Appelé par le build/package du plugin |
| `plugin/composer.lock` | Éviter au démarrage | À ajouter seulement si le plugin devient un package Composer indépendant |

PHPUnit, PHPStan et PHPCS doivent être lancés depuis un emplacement documenté et unique. Le dépôt ne doit pas avoir deux `composer.json` concurrents qui exécutent des scripts différents sans règle explicite. Si le plugin n’a pas de dépendance Composer de production, son `composer.json` local peut être supprimé au profit du `composer.json` racine.

### Contrat des scripts

Tous les chemins canoniques sont à la racine : `scripts/bootstrap-local.sh`, `scripts/bootstrap-ci.sh`, `scripts/doctor.sh`, `scripts/seed-fixtures.sh`, `scripts/reset-fixtures.sh`, `scripts/package-release.sh`, `scripts/check-staging.sh` et `scripts/sanitize-artifacts.sh`. Le dossier `templates/` peut conserver des exemples, mais aucun Makefile ou workflow ne doit appeler un script uniquement présent dans `templates/`.

### Gate de matérialisation

La matérialisation est acceptée lorsque `make install`, `make doctor`, `make reset`, `make validate` et `make package` fonctionnent sur un DDEV propre, que la CI passe sur un runner vierge et que le package est installé sur le WordPress vierge réel. Le rapport doit contenir les versions, les logs, les fixtures, les résultats de tests, le manifeste et le checksum.
