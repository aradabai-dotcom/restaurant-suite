# Rapport de validation V0.3 — Cart Drawer

## Périmètre implémenté

La V0.3 ajoute un endpoint REST `crs/v1/cart/{action}` pour `add`, `update`, `remove` et `refresh`. Toutes les mutations délèguent à `WC()->cart` et utilisent les API CRUD WooCommerce ; aucune table, session ou tarification parallèle n’est créée. La réponse normalisée contient le compteur, le HTML serveur des lignes, le sous-total, les notices, les erreurs et les liens panier/checkout.

Le bundle `cart-drawer.js` constitue le store public unique `window.CRS_CART_STORE`. Il sérialise les mutations par ligne, publie les événements contractuels `crs:cart:add`, `crs:cart:update`, `crs:cart:remove` et `crs:cart:refresh`, ouvre le drawer après ajout, gère l’ajout simple depuis le menu et intercepte les formulaires natifs du Quick View, y compris les attributs de variation. Quick View expose également une API de fermeture `window.CRS_QUICK_VIEW_CLOSE` afin que le drawer puisse fermer déterministement la modale après un ajout réussi. Le drawer est accessible au clavier : rôle dialog, `aria-modal`, focus initial prévu, fermeture Échap, clic extérieur contrôlé, restauration du focus, état de chargement et messages live.

La feuille CSS reste sans framework ni icônes externes, avec état vide, lignes panier, notices, actions, responsive mobile et `prefers-reduced-motion`. Le build copie les deux bundles dans le package WordPress.

## Limites locales

Docker/DDEV n’est pas disponible dans la sandbox ; la validation WordPress intégrée, HPOS et les tests Playwright complets ne sont donc pas revendiqués comme validés localement. Le staging Hostinger est l’environnement WordPress réel utilisé pour les contrôles fonctionnels. Il reste en mode « Boutique bientôt disponible », sans paiement ni commande réelle.

La compatibilité des blocs WooCommerce Cart/Checkout n’est pas annoncée. Les extensions Query Monitor, User Switching et WP Crontrol restent des outils de staging et ne sont pas incluses dans le ZIP client.

## Incidents staging et corrections

Le premier clic d’ajout simple sur staging a initialisé le drawer mais la route REST a retourné HTTP 503 `crs_cart_unavailable`. L’observation a montré que `WC()->cart` n’était pas initialisé dans ce contexte REST, même si WooCommerce était actif et que le panier classique existait sur la page. Le endpoint appelle maintenant `wc_load_cart()` lorsque l’objet WooCommerce ne possède pas encore de panier, relit l’instance `WC()` puis force `get_cart()` avant toute mutation afin de charger la session réellement utilisée. Cette approche est documentée avec les références WooCommerce dans [`woocommerce-cart-api-notes.md`](woocommerce-cart-api-notes.md).

Le scénario staging `add → update → remove → refresh` a ensuite exposé un HTTP 409 sur `remove`. WooCommerce peut retourner `false` alors que la ligne a effectivement disparu ; le endpoint vérifie donc l’état réel de `get_cart()` après un retour négatif et traite l’absence de la clé comme un succès idempotent. Un second cas de suppression par quantité nulle a également été observé pendant l’isolation du comportement ; le contrat final conserve la méthode WooCommerce de suppression et l’idempotence côté réponse.

Le Quick View variable envoyait initialement `variation_id=0` après la sélection Grande. Le endpoint résout désormais l’identifiant avec `WC_Product_Variable::get_matching_variation()` à partir des attributs reçus, puis délègue l’ajout à WooCommerce. Le test staging a confirmé la création d’une ligne Tacos Variable - Grande au prix WooCommerce de 14,00 $, sans commande.

Enfin, plusieurs remplacements WordPress à version identique ont créé temporairement des dossiers suffixés. Le staging a été nettoyé par désactivation contrôlée : seule `restaurant-suite-core-0.3.0-3` est active, tandis que les copies anciennes restent inactives pour rollback. Aucun double runtime Restaurant Suite Core ne subsiste.

## Validation fonctionnelle staging

Les contrôles ont été exécutés sur les fixtures `[CRS TEST]` et n’ont pas touché à des données de production.

| Scénario | Résultat observé |
|---|---|
| Ajout simple depuis le menu | Réussi ; le compteur est synchronisé et le drawer s’ouvre automatiquement après réponse REST |
| Snapshot drawer après ajout | Réussi ; ligne WooCommerce, quantité, total, sous-total et liens sont rendus |
| Mise à jour quantité `1 → 2` | Réussie avec le bouton `[data-crs-cart-increase]` |
| Mise à jour quantité `2 → 1` | Réussie avec le bouton `[data-crs-cart-decrease]` |
| Suppression de la dernière ligne | Réussie ; compteur 0 et état vide affichés |
| État panier vide | Réussi ; message « Votre panier est vide », sous-total 0,00 $ et liens présents |
| Réouverture avec `[data-crs-cart-open]` | Réussie sur panier vide ; `aria-hidden=false` après clic |
| Fermeture Échap | Réussie ; `aria-hidden=true` et focus revenu au bouton d’ouverture |
| Quick View variable Grande | Réussi ; événements `crs:cart:add` puis `crs:quickview:close`, drawer ouvert, ligne Tacos/Grande visible et modale fermée |
| Navigation Panier/Commander | Liens présents ; aucun checkout ni commande finalisé |

Les réponses de diagnostic navigateur ont été limitées au statut, au compteur, aux clés d’état et à la présence des lignes/totaux ; aucun nonce n’a été consigné dans le dépôt public.

## Verdict et gate

**V0.3 est fonctionnellement verte dans les limites déclarées.** Les routes Cart Drawer, l’hydratation REST WooCommerce, l’idempotence de suppression, l’ajout variable résolu côté serveur, le rendu du drawer, l’état vide, les contrôles de quantité, Échap, le focus retour et les liens de continuation ont été vérifiés sur staging. La validation DDEV/HPOS/Playwright complète reste explicitement en attente d’un environnement Docker/DDEV disponible.

La V0.4 ne doit commencer qu’après commit et push de ce rapport, du journal staging, du journal développeur, des notes API officielles, des tests de régression et du package produit. Aucun WhatsApp réel ne sera envoyé dans la suite du projet.
