# Rapport de validation V0.3 — Cart Drawer

## Périmètre implémenté

La V0.3 ajoute un endpoint REST `crs/v1/cart/{action}` pour `add`, `update`, `remove` et `refresh`. Toutes les mutations délèguent à `WC()->cart` et utilisent les API CRUD WooCommerce ; aucune table, session ou tarification parallèle n’est créée. La réponse normalisée contient le compteur, le HTML serveur des lignes, le sous-total, les notices, les erreurs et les liens panier/checkout.

Le bundle `cart-drawer.js` constitue le store public unique `window.CRS_CART_STORE`. Il sérialise les mutations par ligne, publie les événements contractuels `crs:cart:add`, `crs:cart:update`, `crs:cart:remove` et `crs:cart:refresh`, ouvre le drawer après ajout, gère l’ajout simple depuis le menu et intercepte les formulaires natifs du Quick View, y compris les attributs de variation. Le drawer est accessible au clavier : rôle dialog, `aria-modal`, focus initial, fermeture Échap, clic extérieur contrôlé, restauration du focus, état de chargement et messages live.

La feuille CSS reste sans framework ni icônes externes, avec état vide, lignes panier, notices, actions, responsive mobile et `prefers-reduced-motion`. Le build copie les deux bundles dans le package WordPress.

## Limites et gate staging

Docker/DDEV n’est pas disponible dans la sandbox ; la validation WordPress intégrée, HPOS et les tests Playwright complets ne sont donc pas revendiqués comme validés localement. Le staging Hostinger reste en mode « Boutique bientôt disponible », sans paiement ni commande réelle. Le déploiement V0.3, les assertions DOM du drawer, les actions add/update/remove/refresh et l’observation des appels réseau doivent être ajoutés au journal staging après installation du package.

La compatibilité des blocs WooCommerce Cart/Checkout n’est pas annoncée. Les extensions Query Monitor, User Switching et WP Crontrol restent des outils de staging et ne sont pas incluses dans le ZIP client.

## Incident staging et correctif

Le premier clic d’ajout simple sur staging a initialisé le drawer mais la route REST a retourné HTTP 503 `crs_cart_unavailable`. L’observation a montré que `WC()->cart` n’était pas initialisé dans ce contexte REST, même si WooCommerce était actif et que le panier classique existait sur la page. Le endpoint appelle maintenant `wc_load_cart()` lorsque l’objet WooCommerce ne possède pas encore de panier, puis relit `WC()->cart`. Le correctif est passé localement par Parallel Lint, PHPCS, PHPStan, PHPUnit, build, ESLint, Stylelint, Vitest, contrats et packaging ; il doit être redéployé sur le staging avant validation finale.
